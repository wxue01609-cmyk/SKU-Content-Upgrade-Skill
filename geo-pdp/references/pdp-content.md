# 商品详情页（PDP）改造规范

目标：让 AI 能从 PDP 直接提取“这是什么、适合谁、关键参数、和同类的取舍、买了以后怎样”，同时让从 AI 跳转来的用户能直接下单。所有硬事实只用证据账本中可发布的 claim。

## 一、模块（按页面顺序）

| 模块 | 内容 | 要求 |
|---|---|---|
| 1. 商品标题 | 品牌 + 型号/系列 + 品类 + 1-2 个区分属性（规格、场景） | ≤150 字符；不堆关键词；与 feed 标题一致或仅变体差异 |
| 2. 核心答案段 | 2-3 句：是什么、适合谁/什么场景、最关键的 1-2 个参数、主要限制 | 脱离页面也能成立；就是 manifest 的 `core_answer` |
| 3. 关键卖点 | 3-5 条，每条“属性 → 对用户意味着什么”，每条可对应一个 claim | 不用 best / #1 / ultimate 等绝对化词 |
| 4. 参数表 | 规格逐项列出（尺寸、重量、材质、容量、兼容性、认证…） | 必须是 HTML 文本表格，不能只在图片里 |
| 5. 适用与不适用 | 适合的场景/人群；不适合的情况 | 真实取舍提升可信度，也减少退货 |
| 6. 兼容性 / 尺码 / 选型 | 兼容型号清单、尺码表、变体差异 | 变体之间的差异写清楚 |
| 7. 购买信息 | 价格与优惠规则、配送范围与时效、退货期限与条件、保修 | 文本可见，与 feed 的 shipping / return 字段一致 |
| 8. 常见问题 | 4-8 个，来自问题族中的验证类、顾虑类、交易类问法 | 原问句优先；答案先给结论 |
| 9. 评论摘要 | 评分、评论数、高频优点与高频顾虑 | 只用真实评论数据（`review_stat` claim）；不得只在 schema 中出现 |
| 10. 对比模块（可选） | 与同品牌其他型号或同类方案的对比表 | 点名竞品需证据与 `competitor_naming_allowed`；默认只做自家型号对比 |

## 二、写法
- **原始 HTML 可读**：标题、价格、核心答案、参数表、购买信息必须出现在服务端输出的 HTML 中，不依赖 JS 渲染或折叠后异步加载。
- **问题族覆盖**：每个关联 topic 的核心问法在页面上有直接答案（卖点、参数、FAQ 中任一处）。
- **语言**：目标市场语言，简洁、技术化，不写营销腔。
- **一致性**：同一事实在 PDP、feed、schema、Amazon listing 中的数值完全一致；有差异时以证据账本为准，并在交付说明中列出需要同步修改的位置。
- **不做**：伪造评论、虚构用户、写未核实的认证/防水/续航等参数、写“限时”“仅剩”类压力话术。

## 三、交付物
`deliverables/<change_id>/`：
- `before_after.md`：逐模块对照表（模块 | 现状 | 改后 | 改动原因 | 依据的 claim_id）。现状取自 PDP 导出或线上页面抓取，注明日期。
- `pdp.html`：改后正文 HTML 片段（只含正文模块，不含站点模板），属性用双引号的标准 HTML 即可。
- `product.jsonld`：若本卡同时包含 schema（或另有 `product_schema` 卡），见 product-schema.md。
- `manifest.json`：`core_answer`、`claims_used`、`target_url`、`internal_links`。

Shopify 等平台客户如需批量导入，另附 `import.csv`（字段按客户平台的导入模板），在 manifest 中 `role` 记为 `feed_csv`。
